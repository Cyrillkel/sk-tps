# СК «Техпромстрой»

Поэтапная разработка сайта об инженерных и технологических системах на Next.js App Router, React, TypeScript и Tailwind CSS. Контент и фотографии: https://sk-tps.ru/. Композиция hero: https://sigurd-promo.ru/new/.

## Запуск

Нужны Node.js 20.19+ и pnpm 10.10.0.

```bash
cd frontend
pnpm install
pnpm dev
```

Сайт доступен на http://localhost:3000.

```bash
pnpm lint
pnpm typecheck
pnpm build:static
```

`build:static` использует Webpack и создаёт статический сайт в `frontend/out/`, как в CI. Для стандартного сервера Next.js доступен `pnpm build`. Если окружение запрещает служебный локальный порт Turbopack, для разработки используйте `pnpm dev --webpack`.

## Структура

```text
frontend/
├── app/                 # Маршруты и специальные файлы Next.js
└── src/
    ├── _app/            # Корневой layout, metadata и глобальные стили
    ├── _pages/          # Композиция страниц
    ├── widgets/         # Разделы главной, содержимое услуг и проектов, шапка и подвал
    ├── features/        # Навигация, галереи, слайдеры, тема и связь
    ├── entities/        # Компания, услуги, проекты и география работ
    └── shared/          # Общие компоненты без бизнес-логики
```

Слои FSD `_app` и `_pages` названы с префиксом, чтобы избежать конфликта с зарезервированными папками Next.js. Файлы `app/` подключают страницы через публичные API слайсов. Импорты направлены в нижние слои; между слайсами одного слоя импортов нет. Внутри слайса используются относительные импорты, снаружи — его `index.ts`. ESLint проверяет направления импортов и запрет обращения к внутренним файлам слайсов через alias.

Компоненты по умолчанию серверные. Клиентские границы нужны для интерактивных элементов: навигации, галерей, слайдеров и темы. Цвета и шрифты заданы токенами в `src/_app/styles/globals.css`. Общий контейнер занимает всю ширину окна с боковыми отступами 20, 32 или 40 px по брейкпоинтам, без фиксированного `max-width`.

## Текущий объём

Главная содержит направления услуг, выполненные инженерные проекты, сведения о компании, документы, благодарственные письма, порядок работы, географию и контакты. Блок «География работ» содержит ссылки на 28 городских страниц по адресам `/uslugi-<город>/`, например `/uslugi-kaluga/`.

Логотип находится в `public/brand/logo.svg`: это векторная копия [полного PNG с исходного сайта](https://static.tildacdn.com/tild3932-3138-4064-a136-663239653362/photo.png), с прозрачным фоном и надписью в контурах. Favicon представлен SVG, ICO и Apple touch icon в `app/`. Общие SVG-иконки находятся в `shared/ui/icons.tsx`.

`/seti/` — каталог инженерных и технологических систем. Один шаблон обслуживает 11 страниц услуг с отдельным содержимым, составом работ, вопросами и связанными проектами. Данные находятся в `entities/service`. Прочистка и обслуживание канализации входят в комплексное сервисное обслуживание; отдельная страница прочистки не генерируется. Монтаж и реконструкция канализационных сетей остаются видом инженерных работ.

Компания не разрабатывает проекты: монтаж предлагается по готовой проектной документации заказчика. Портфолио подписано «Наши работы». При переносе контента нельзя добавлять предложения проектирования или упоминания обслуживания канализации вне комплексного сервисного обслуживания; ограничения закреплены в `AGENTS.md`.

`/proekty/` — портфолио из 23 проектов с исходного sk-tps.ru. В него перенесены все 205 уникальных фотографий из карточек и внутренних галерей. Исторические проекты монтажа конструкций и ремонта сохранены в портфолио; строительство зданий и капитальный ремонт отдельными услугами не предлагаются. Основные 22 адреса проектов сохранены, для найденной в sitemap страницы `/page139288356.html` выбран понятный адрес `/rekonstrukciya-dezbarera/`. Перед заменой действующего сайта для старого адреса потребуется 301-редирект.

Новые работы от заказчика добавляются отдельно от миграции: исходные фото кладутся в `frontend/portfolio-sources/<адрес-страницы>/`, затем `cd frontend && node scripts/prepare-portfolio-images.mjs` создаёт WebP (полная версия до 2200 px и превью до 640 px) с водяным знаком — диагональной сеткой из `public/brand/logo.svg`, как на перенесённых фото, — в `public/images/portfolio/` и манифест `portfolio-photos.json`. Название, категория, описание, список выполненных работ («Выполнили …»), связанные услуги и обложка задаются в `entities/project/model/portfolio.ts`. Такие работы идут первыми в каруселях; список работ выводится на странице объекта. `scripts/verify-content.py` проверяет и их. Первая работа — прокладка кабельной линии 0,4 кВ (электромонтаж).

Шаблоны всех 23 объектов и 11 услуг используют общие секции с главной: допуски и лицензии, варианты сотрудничества, этапы работы, география, обратная связь, преимущества, благодарственные письма, клиенты и отзывы. Они подключены через существующие `Home*`-компоненты в том же порядке, что на главной, после собственного содержимого страницы. Полный блок направлений услуг отображается на главной, городских страницах и в каталоге `/seti/`; в содержимом страниц объектов и услуг сохранены компактные ссылки на связанные услуги. Блок «О компании» находится на главной и городских страницах. Форма связи встречается один раз; собственные первые экраны, галереи и подборки работ сохранены. Ссылка на допуски в описании услуги ведёт к документам на этой же странице.

Фотографии проектов хранятся локально в WebP: полные версии до 2200 px и превью до 640 px. Карточки и сетки используют превью с ленивой загрузкой, открытая галерея — полную версию. Галереи поддерживают стрелки, клавиатуру, свайпы и циклическое переключение; при увеличении снимка свайп не меняет фото. Мобильный слайдер услуг также зациклен. В правом нижнем углу расположена раскрывающаяся кнопка мессенджеров.

Карточки выполненных работ используют общий `shared/ui/CardCarousel` на Swiper: 1,3 карточки до 768 px, 2,3 от 768 px и 3,3 от 1024 px. Компонент подключён на главной, в каталоге работ, на страницах услуг и объектов, а также в шаблоне города. Есть зацикливание, крупные стрелки по бокам карточек, свайп, перетаскивание мышью и клавиатурное управление внутри карусели. Движение учитывает настройку уменьшенной анимации. Для 2–4 карточек повторяется полный набор слайдов, чтобы Swiper мог поддерживать непрерывный цикл; единственная карточка показывается без навигации. Все карточки и ссылки присутствуют в серверном HTML.

Документы, лицензии и благодарственные письма открываются на весь экран без рамки и панелей, как на исходном сайте: закрытие и увеличение расположены в углу, стрелки — по бокам поверх просмотра. Лист занимает доступную высоту с сохранением пропорций; на компьютере оставлен отступ 15 px по краям, на телефоне отступов нет. Фотографии объектов открываются в отдельном окне с панелью инструментов и навигацией. Кнопка увеличения показывает изображение с прокруткой в исходном размере или минимум в 1,5 раза крупнее текущего отображения.

Автопрокрутка карточек работ реализована в самом `CardCarousel`, без модуля Swiper Autoplay: модуль использует общий параметр `speed` и для доводки после свайпа, из‑за чего на телефоне карточки «доплывали» 1,8 с. Сейчас свайп, перетаскивание и стрелки доводят карточку за 350 мс с замедлением, а автопрокрутка — пауза 3 секунды и плавный переход 1800 мс с разгоном и замедлением. Для смены карточки достаточно короткого броска или сдвига на четверть карточки. Автопрокрутка приостанавливается, пока карусель трогают пальцем или мышью, при наведении мыши, вне экрана и в скрытой вкладке. На телефонах (до 768 px, сенсорный ввод) стрелки скрыты: листание свайпом, следующая карточка видна у края. При системной настройке уменьшенного движения или единственной карточке автопрокрутка отключена.

Городские страницы используют нашу главную: общий `HomeHero`, направления услуг, о компании, документы, сотрудничество, этапы работы, географию, форму связи, преимущества, письма, клиентов и отзывы. Для города заданы собственные первый экран, метаданные, описание подготовки работ и вопросы. Рабочие тексты разнесены по трём файлам `city-content-*.ts` в `entities/geography/model`; их можно уточнять после подготовки семантического ядра. Местные проекты необязательны и показываются только при подтверждённой привязке к этому городу; сейчас городские подборки пусты. `sitemap.xml` содержит все 67 страниц; каждая имеет собственный canonical будущего основного домена. Ссылки и sitemap используют городские адреса `/uslugi-<город>/`. Демо на IP по-прежнему закрыто от индексации заголовком Nginx. Подробности — в [docs/content-and-geography.md](docs/content-and-geography.md).

Для статического сайта карточки услуг используют готовые responsive WebP через `picture/srcset`. Варианты хранятся рядом с исходниками; повторная подготовка: `cd frontend && node scripts/prepare-responsive-images.mjs`. Скрипт использует уже установленный с Next.js `sharp`. Разбор предоставленного отчёта PageSpeed и ограничения демо описаны в [docs/performance-audit.md](docs/performance-audit.md).

`/contacts/` содержит телефон, почту и мессенджеры, общую форму заявки, адрес компании, реквизиты и карту Яндекса с ленивой загрузкой. Кнопки связи в шапке и hero ведут на эту страницу. Страница 404 оформлена инженерной SVG-схемой и содержит ссылки на главную, услуги, работы и контакты. Обе страницы поддерживают мобильные экраны и две темы; оформление находится в локальных CSS modules соответствующих слайсов.

Светлая и тёмная темы доступны в шапке. Выбор хранится в `localStorage` под ключом `sk-tps-theme`, при первом визите учитывается системная тема. Скрипт в корневом layout применяет тему до отрисовки, переключатель подписывается на её изменения через `useSyncExternalStore`. Цвета шапки, меню и hero заданы семантическими CSS-токенами; вариант логотипа для тёмного фона сохраняет фирменный знак и использует светлую надпись.

Формы обратной связи сначала проверяют поля в браузере схемой Zod (`zod/mini`, `features/feedback-form/model/feedback-schema.ts`) и показывают ошибки под полями; правила совпадают с серверными. Затем форма отправляет заявку `POST /api/feedback` в JSON. Её принимает небольшой сервис `backend/feedback/` на стандартной библиотеке Python, без зависимостей. `request.py` проверяет поля и собирает письмо. `delivery.py` отправляет его через API [Resend](https://resend.com), если задан `RESEND_API_KEY`, иначе — через SMTP. `server.py` — тонкий HTTP-обработчик на `127.0.0.1:8081`. Получатели перечисляются через запятую в `FEEDBACK_TO`, отправитель для Resend — `FEEDBACK_FROM` на подтверждённом в Resend домене (`noreply@sk-tps.ru`). Если посетитель указал email, он становится `Reply-To`. Сайт по-прежнему статический: Nginx проксирует только этот адрес и ограничивает частоту запросов. Защита от спама: скрытое поле-ловушка `website`, лимит Nginx и серверная проверка полей. Базы данных нет, заявки на сервере не хранятся.

Resend только отправляет письма. Адреса из `FEEDBACK_TO` должны принимать почту сами: у домена sk-tps.ru для этого нужен работающий почтовый ящик и MX-записи. Для Resend в DNS добавляются записи, которые показывает его панель после добавления домена: DKIM `resend._domainkey`, а также MX и SPF поддомена `send`. MX самого домена они не затрагивают. Resend — зарубежный сервис: имя и телефон из заявки передаются за пределы РФ, а это по 152-ФЗ трансграничная передача персональных данных.

Установка или обновление сервиса на VPS (root, однократно и при изменении `backend/feedback/`): скопировать на сервер `deploy/` и `backend/feedback/` с сохранением структуры и настройки (как в локальном `.env.local`), затем выполнить `bash deploy/install-feedback.sh /path/to/feedback.env`. Скрипт кладёт код в `/opt/sk-tps-feedback`, настройки — в `/etc/sk-tps/feedback.env` (0600, root). Он проверяет ключ Resend или SMTP-логин без отправки письма, запускает `sk-tps-feedback.service` в песочнице systemd (`DynamicUser`) и применяет `deploy/nginx.conf`; если `nginx -t` не прошёл, возвращает прежний конфиг. CI сервис не обновляет: ключ деплоя публикует только статические файлы. Журнал: `journalctl -u sk-tps-feedback`, персональные данные в него не пишутся.

Локальная проверка: запустить сервис с переменными из `.env.local` (`set -a; . ../.env.local; set +a; python3 ../backend/feedback/server.py`) и `pnpm dev`. В режиме разработки Next.js проксирует `/api/feedback` на `FEEDBACK_SERVICE_URL` (по умолчанию `http://127.0.0.1:8081`). Тесты: `python3 -B -m unittest discover -s backend/feedback -p 'test_*.py'`.

## Домен и HTTPS

DNS домена sk-tps.ru находится в Timeweb Cloud (NS `ns1/ns2.timeweb.ru`, `ns3/ns4.timeweb.org`). Записи A для `sk-tps.ru` и `www` указывают на VPS 177.203.49.191. Почта остаётся в Яндекс 360: MX `mx.yandex.net`, SPF `v=spf1 redirect=_spf.yandex.net`. Записи Resend (`resend._domainkey`, `rsend`, `send`) нужны только для отправки заявок. При правке DNS их и MX не трогать.

Сайт работает по адресу `https://sk-tps.ru`. `http://` и `www` переадресуются туда с кодом 301; демо по IP остаётся на HTTP, через него CI проверяет выкладку. Сертификат Let's Encrypt выпускает и продлевает certbot (`certbot.timer`) через `/var/www/letsencrypt`; после продления Nginx перезагружается автоматически. Первичная настройка выполнена скриптом `deploy/enable-https.sh` от root. `deploy/nginx.conf` ссылается на сертификат, поэтому на новом сервере его применяют только после этого скрипта. Индексация домена пока закрыта тем же заголовком `X-Robots-Tag`, что и демо: её откроют после 301-редиректов со старых адресов Тильды.

## Демо и автодеплой

Адрес после настройки VPS: http://177.203.49.191/. Workflow `.github/workflows/deploy.yml` запускается после push в `main` или вручную через Actions. Он устанавливает зависимости по lockfile, проверяет код, выполняет `pnpm build:static`, передаёт каталог `out/` по SSH и проверяет идентификатор опубликованной версии по HTTP.

Для демо используется статическая выгрузка Next.js (`NEXT_OUTPUT=export`). Серверные функции при такой сборке недоступны. Обычная сборка `pnpm build` сохраняет стандартный режим Next.js. При добавлении серверной логики способ размещения нужно изменить.

На VPS нужен Nginx и пользователь `deploy-sk-tps` без `sudo`. Однократную настройку выполняет `deploy/bootstrap.sh`, которому передаётся только публичный ключ CI. Перед запуском скрипта требуется согласование установки пакетов и изменения конфигурации сервера. Ключ CI разрешает только команду публикации; права root и обычный shell ему не предоставляются. Публичный host key сервера закреплён в `deploy/known_hosts` и получен через существующее проверенное SSH-соединение.

Приватный ключ добавляется напрямую в GitHub: **Settings → Secrets and variables → Actions → New repository secret**, имя `SK_TPS_DEPLOY_KEY`. Значение ключа не отправляется в чат и не попадает в Git. Локальный файл ключа хранится в игнорируемом `.local/deploy/ci_ed25519` с правами `0600`. При доступном GitHub CLI секрет можно добавить без вывода ключа: `gh secret set SK_TPS_DEPLOY_KEY --repo Cyrillkel/sk-tps < .local/deploy/ci_ed25519`.

Каждая сборка загружается в отдельный каталог `/srv/sk-tps/releases/`. После проверки обязательных файлов атомарно переключается ссылка `current`; ошибочная загрузка не затрагивает текущую версию. Хешированные JS/CSS предыдущих версий сохраняются в `shared/`, чтобы открытые вкладки могли загрузить старые ресурсы. Автоматического удаления релизов пока нет. Демонстрационный Nginx добавляет `X-Robots-Tag: noindex, nofollow, noarchive` и раздаёт сайт по HTTP на порту 80. Конфигурация в `deploy/nginx.conf` включает gzip для CSS, JS, JSON, SVG и текста, кеш медиа на 7 дней и хешированных ресурсов на год. Обычный CI публикует только статические файлы; изменение конфигурации Nginx нужно отдельно применить на сервере и проверить `nginx -t` перед перезагрузкой. Повторно запускать весь bootstrap ради этой правки не требуется.
